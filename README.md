# 浏览器 P2P 工具（WebRTC：文件直传 / 屏幕共享 / 通话 / 聊天 / 剪贴板）

基于 **WebRTC** 的纯浏览器端 P2P 工具（支持IPv6）。**无需任何后端服务器**，两个设备通过“复制粘贴”或“扫码”完成信令交换，数据在浏览器之间点对点直传。有需要的情况下依赖公开 STUN 服务器辅助 NAT 穿透。除**文件直传**外，还内置**屏幕共享（屏幕监看）**、**实时通话**、**聊天**与**剪贴板同步**等功能。

## 特性

- 对称对等：两端角色对等，均可收发文件。
- 手动信令：会话码通过**复制粘贴**或**二维码**在带外交换，不经过任何第三方服务器。
- 可靠传输：`{ ordered: true }` 有序可靠 DataChannel；**64KB 分块** + **背压控制**（监控 `bufferedAmount`）。
- 端到端加密（可选）：**文件与聊天**数据可叠加 AES-GCM 256 双层加密，密钥随会话码手动交换；所有功能（文件 / 屏幕共享 / 通话 / 聊天）另受 WebRTC 原生 DTLS-SRTP 传输加密保护，并内置会话指纹（MITM）校验——指纹不匹配即关闭通道。
- 完整性校验：发送端计算 SHA-256 并随元信息下发，接收端组装后比对。
- 断点续传：同一连接内，接收端在收到 `file-complete` 后若发现缺块，通过 `resume-request` 仅请求缺失分块，发送端 `onResumeRequest` 补传（不重发整文件）。已收分块同时写入 **IndexedDB** 留档。
- 大文件流式写盘（可选，默认开启）：接收端通过 **File System Access API**（`showSaveFilePicker` + 可写流）将分块**边收边存**到磁盘，全程不把整文件放入内存，彻底避免 `out of memory`。从磁盘流式读取做 SHA-256 校验，**不占用内存**。需 Chrome / Edge 且安全上下文（localhost / HTTPS）。不支持的浏览器自动回退为「内存拼装后下载」（大文件可能内存溢出）。
- 屏幕共享（屏幕监看）：发起方可在连接前**预选要共享的屏幕/窗口**，连接后自动开始共享；支持 **帧率、码率** 以及「流畅优先 / 清晰度优先」模式。
- 发送端自适应（ABR）：监看端检测到花屏/卡顿后通过 DataChannel 下发指令，发送端自动**降档**（码率 / 帧率 / 分辨率），网络恢复后自动回升；监看端同时具备花屏检测与自愈（请求关键帧）。
- 实时统计：发送端在本地预览**上方**显示「发出去」的分辨率·码率·帧率（取自 `outbound-rtp`，即真正下发的参数）；监看端在画面**下方**显示收到流的分辨率·码率·帧率·卡顿秒数。
- 设置记忆：屏幕共享的帧率 / 码率会被写入 `localStorage`（键 `bsScreenProfile`），下次打开自动还原为控件默认值。
- 浅色界面：整套配色已切换为浅色主题；功能中心「先选屏 / 设备测试」按钮为左右 **7:3** 布局。

## 运行

WebRTC 与摄像头需要**安全上下文**，需要对应的服务器。

在浏览器打开 `http://localhost:8000` 或者 https 的服务地址。

## 使用步骤

1. **选择身份**：设备 A 点「发起方」→ 自动生成连接码（可复制 / 显示二维码）；设备 B 点「加入方」→ 粘贴 / 扫描 A 的连接码 → 点「生成应答码」。
2. **交换应答**：设备 B 把应答码复制 / 展示二维码发回 A；A 在「粘贴对方的应答码」处粘贴 / 扫描 → 点「完成连接」。
3. 两端 `DataChannel` 建立，状态变「已连接」并自动进入**功能中心**，选择「聊天 / 通话 / 屏幕监看 / 剪贴板同步」。

> 各功能页均有「← 返回」键：聊天 / 通话 / 屏幕 / 剪贴板返回功能中心；功能中心返回连接码页；连接码页返回身份选择。

## 屏幕共享

1. **预选屏幕**：在功能中心点「🖥️ 先选好要共享的屏幕」，提前 `getDisplayMedia` 选好源（连接后自动开始共享）；「🧪 设备测试」用于本地摄像头/麦克风自检。两按钮为 7:3 左右布局。
2. **参数设置**：`帧率`（5/10/15/30）与 `码率`（200–8000 kbps）两控件，开始共享时即作为实际下发上限；这两个值会自动记忆，下次进入页面自动恢复为上次设置。
3. **模式**：`流畅优先` 弱网卡顿时优先降码率；`清晰度优先` 优先降帧率保清晰。
4. **自适应（ABR）**：监看端每秒检测 `framesDropped` / `pliCount` / `freezeCount` / 卡顿秒数，超阈值即通过 DataChannel 让发送端降一档，恢复后升档；发送端按「分辨率阶梯 × 监看端分辨率缩放 ÷ 缩放放大」计算实际下发分辨率（`scaleResolutionDownBy`）。
5. **两端统计**：
   - 发送端：`screenLocal` 上方 `发送：WxH · kbps · fps`，数据来自 `outbound-rtp`（已编码、含 ABR 降采样后的真实输出）。
   - 监看端：画面上方显示收到流的 `分辨率 · 码率 · 帧率 · 卡顿 Ns`。

> **关于码率**：WebRTC 视频的「码率」是**编码上限**而非恒定目标值。静态/低复杂度画面编码器几乎不耗带宽，实际只有几十~几百 kbps 属正常；分享视频/快速滚动等内容时才会爬向你所设的上限。丢包 < 0.1% 基本不会触发 ABR 降档。

## 实现要点（对照计划）

- **信令压缩**：新码默认采用**自研 LZH（LZ77 + 哈夫曼，纯 JS，见 `js/lzh.js`）**压缩，零浏览器依赖，旧 Safari 等也可压可解。会话码以 Base64URL 承载，正文首位为格式标识：`3`=LZH 压缩、`2`=浏览器原生 `deflate-raw`、`1`=gzip、`0`=明文（`1/2` 仅为旧码兼容保留，新生成一律 `3`）；SDP 内联字段（`z`）同样用 LZH，并以 `c:'lzh'` 标记。SDP 仅剔除候选行 / 指纹行 / 可选行（extmap、rtcp-fb、rtcp-rsize）；压缩无收益时自动回退明文（纯 Base64URL）。
- **分块帧**：明文 `tag(1)+chunkIndex(4)+fileId(4)+payload`；加密 `tag(1)+chunkIndex(4)+fileId(4)+ivRandom(8)+密文`，IV 由「分块索引 + 8 字节随机数」构成。
- **背压**：`send()` 只是把分块塞进发送缓冲区就返回，而非真正发出。`bufferedAmount` 表示「已发但未确认送达」的字节数；当其超过 **16MB** 阈值（网络跟不上发送速度）时暂停发送并轮询，待缓冲消化到阈值以下再继续。这样内存占用有上限，发送速率自动贴近真实网络吞吐，避免几 GB 文件把内存撑爆。
- **安全**：整条连接（文件 / 屏幕共享 / 通话 / 聊天）均受 **WebRTC 原生 DTLS-SRTP** 传输加密保护；连接建立后双方交换 `sessionFingerprint`（DTLS 证书指纹）比对，不一致即判定中间人攻击并关闭通道——该 MITM 检查对连接内所有流量生效。此外，**文件与聊天**数据可再叠加一层**可选 AES-GCM 双层加密**（应用层）；屏幕共享 / 通话的媒体流走 DTLS-SRTP，不单独走该 AES-GCM 开关。
- **断点续传**：每收到分块即 `idbSaveChunk` 写入 IndexedDB，元信息 `idbSaveMeta`；接收端在 `file-complete` 后计算缺失分块并 `resume-request` 补传，发送端 `onResumeRequest` 仅重发缺失分块。**注意**：此续传仅在连接保持时有效——页面刷新会断开连接，且当前重连不会从 IndexedDB 恢复（历史面板 `idbGetAll` / `loadHistory` 已停用），刷新后需整体重传。（如果发送方刷新后没有重新发送，接收方压根无法断点续传）

## 已知限制

- 大文件流式落盘依赖 **File System Access API**（Chrome / Edge 且安全上下文）；不支持的浏览器回退为「内存拼装后下载」，数 GB 文件可能内存溢出。默认已开启流式落盘。
- 摄像头扫码需安全上下文（见“运行”）。
- 网页刷新、IP变化、断连，都需要重建连接；
- 剪贴板同步要求焦点位于浏览器，因此无法做到后台实时浏览器同步，建议小窗、浮窗使用；
